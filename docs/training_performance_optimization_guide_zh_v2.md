# 深度学习训练全链路性能优化指南

> **适用范围**：深度学习训练系统，重点面向 PyTorch；覆盖单卡、单机多卡及多机训练，适用于视觉、多模态、视觉语言动作模型（VLA）等任务。  
> **目标**：在满足正确性、模型质量和资源约束的前提下，缩短完成有效训练的时间。  
> **版本**：v2，更新于 2026-10-05。
> **资料核查日期**：2026-10-05。涉及具体接口时，应使用与项目锁定版本匹配的官方文档。

## 1. 核心原则与使用方式

本文从原始性能优化案例中提炼“先保证正确性，再分析整条训练链路，随系统变化反复调优”的方法，不将其特定模型、平台、超参数或加速幅度作为通用承诺。[1] v2 进一步依据补充材料，按“模型基座数值精度、模型适配语义与初始化、数据分片与增强”三个层面完善正确性检查，并补充权重转换与部署验收。[13]

**来源与建议的边界**：案例经验标注对应来源；测试流程、代码示例和验收模板是本指南的通用化工程建议。对补充材料中不宜泛化的框架默认行为，另据官方资料核查，并在文末“本次更新说明”列明，不将来源的个案描述直接替换成未经说明的通用结论。

**优化对象是完整训练任务，而不是某个孤立算子；最终依据是经过正确性验证的端到端收益。**

将优化过程组织为以下闭环：

```text
建立可信基线
    → 测量端到端性能与资源使用
    → 提出有证据支持的瓶颈假设
    → 实施最小可回滚改动
    → 验证正确性与实际收益
    → 更新配置与资源预算
    → 重新测量，决定下一步
```

开始前先区分三种工作：

| 工作类别 | 允许改变的内容 | 结果如何解释 |
| --- | --- | --- |
| 实现修复与跨框架迁移 | 修复数值、结构、数据或权重映射差异，恢复约定的训练语义 | 先建立可信实现；存在正确性缺陷的旧版不能直接充当等价性能基线 |
| 等价训练的系统优化 | 执行组织、通信调度、数据传输表示、编译方式等；训练语义需验证 | 可以在统一训练协议下比较性能 |
| 训练方案或任务调整 | 有效输入分辨率、真实相机数量、序列长度、动作预测长度、损失、训练数据量、全局批大小等 | 必须额外比较任务质量，不能只报告吞吐加速 |

删除本来就不参与任务的占位输入，与删除真实有效观测，不属于同一类改动。改变精度模式、算子后端或批次组织，也不能直接假定训练结果等价。

有实现对齐问题时，先完成“修复与对齐”，再以修复后的版本衡量系统优化收益，分别报告两阶段结果。

单卡任务跳过分布式通信调优；没有显存压力的任务不应仅为使用 FSDP 而引入分片。优先评估当前系统实际暴露的问题。

## 2. 定义优化目标与可比较的基线

### 2.1 同时保留两类成绩

**稳态性能**回答“训练循环持续运行时有多快”。**作业性能**回答“从启动到产出满足目标的模型，实际需要多长时间”。两者应分别记录。

建议至少报告：

| 指标 | 推荐口径 |
| --- | --- |
| 有效吞吐 | 测量窗口内完成处理的有效样本数 ÷ 窗口实际耗时 |
| 优化器更新耗时 | 完成一次参数更新的耗时；包括对应的全部梯度累积微步 |
| 波动 | 更新耗时的中位数、P95，以及多次测量的离散程度 |
| 显存 | 各卡峰值 allocated、reserved；另记设备级占用 |
| 数据等待与通信暴露 | 哪些等待实际延长了训练关键路径，以及对应耗时 |
| 完整作业耗时 | 启动、编译、训练、评估、保存和必要数据准备的实际墙钟时间 |
| 训练质量 | 预先约定的验证指标；策略训练应包含对应任务评估 |

可变长度任务同时记录非填充 token/s 或其他有效工作量。固定 token 预算下的 samples/s，与固定样本数下的 samples/s，不能脱离长度分布直接比较。记录重复采样、丢弃尾批和分布式补齐策略，防止计数口径变化制造“加速”。

多卡数据审计时，另记同一测量窗口的**已处理样本条目数、去重后的样本身份数，以及非预期重复比例**。这是排查分片错误的诊断口径，不是把有意重复采样判为无效，也不能将“唯一 sample_id 数”解释成统计独立样本数。样本身份应包含足以区分数据版本、轨迹和时间步的字段；检查方法见第 5.4 节。

### 2.2 冻结基线清单

| 类别 | 必须记录的内容 |
| --- | --- |
| 硬件与拓扑 | GPU 数量、型号、显存，CPU 配额、内存、存储位置，卡间和机间连接 |
| 软件与代码 | 代码提交、依赖锁文件、驱动、计算后端、通信库、编译器、启动命令 |
| 模型与数据 | 模型配置、初始权重、训练参数范围、数据版本、划分、采样与预处理 |
| 数值与训练 | 参数和计算精度、损失定义及归一化、优化器、学习率调度、裁剪、随机状态 |
| 批次组织 | 每个数据并行副本的微批大小、数据并行副本数、梯度累积次数、尾批处理 |
| 测量条件 | 预热规则、计时窗口、重复次数、缓存状态、日志/评估/保存频率 |

在微批等长、各副本批大小相同的普通数据并行训练中：

```text
全局批大小 = 每个数据并行副本的微批大小 × 数据并行副本数 × 梯度累积次数
```

这里的“数据并行副本数”不一定等于总 GPU 数；混合张量并行或流水线并行时尤其需要区分。变长批次、按 token 归一化的损失和不完整尾批，应按实际参与更新的样本及权重核算。

若为改善硬件利用率而增大微批，可以在允许时减少累积次数以保持全局批大小。但仍需检查损失缩放、批次相关层、随机算子和梯度同步语义，不能只验证上述乘积相同。

## 3. 先设置正确性门槛

### 3.1 采用分层回归，而不是只看平均 loss

建议建立可重复运行的小型回归测试集，并将以下检查与优化改动绑定：

| 验证层级 | 核心检查 |
| --- | --- |
| 输入与标签 | 样本身份、图像/序列布局、时间对齐、掩码、标签、归一化、增强参数 |
| 前向与损失 | 关键中间输出、最终预测、逐样本或逐 token 损失及其聚合方式 |
| 梯度与参数更新 | 参数是否获得正确梯度、梯度大小、裁剪、一次更新后的参数及优化器状态 |
| 分布式语义 | 数据划分、归约与缩放、累积边界、各进程参数一致性、动态分支执行 |
| 保存与恢复 | 模型、优化器、调度器、随机状态、采样进度；检查继续训练的一致性 |
| 训练与任务质量 | 短程趋势检查，以及与预期用途匹配的验证集或任务评估 |

单步对照尽可能使用同一初始状态、相同输入、相同噪声和增强参数。仅设置同一个随机种子，不应替代对实际输入与随机过程的检查。

### 3.2 明确三种“相同”

**逐位相同**适用于能够严格保持数值表示的变换。**容差内一致**适用于允许有限数值误差的计算改写。**任务质量不劣化**用于判断完整训练结果是否满足用途。三者不能互相替代。

浮点计算顺序、设备和版本变化可能导致数值差异，即使数学表达式等价，也不保证逐位相同。[2] 因此应预先为不同张量和精度设定容差，例如采用：

```text
|candidate - reference| ≤ atol + rtol × |reference|
```

同时检查非有限值、最大误差和误差分布，不只比较平均数。这里不规定跨模型通用的 atol/rtol；阈值必须由数值精度、张量尺度及任务敏感性决定。

完整训练的验收应预先约定允许的指标退化和不确定性评估方式。对波动较大的策略成功率，可使用多个训练种子与固定评估场景。短程 loss 接近只能支持短程数值行为接近，不能单独证明所有任务上的最终质量相同。

### 3.3 跨实现对齐：先固定参考，再定位第一处分歧

补充材料新增的关键经验是：不能仅凭模型名称、层数或超参数相同，就认定两个框架实现等价；应将组件输出、梯度、数据和 checkpoint 纳入同一套验证。[13] 本指南建议按以下方式建立“对齐契约”：

| 契约项 | 应固定或保存的内容 |
| --- | --- |
| 参考对象 | 经项目确认的参考实现、提交、配置、依赖版本与权重；不能仅写“官方版” |
| 固定测试输入 | 原始样本及最终模型输入、标签、mask、位置索引、噪声、时间变量、增强参数 |
| 数值路径 | 各模块参数/计算/归约精度、算子近似方式、后端和 cast 边界 |
| 状态与比较点 | 训练/评估模式、关键中间张量、对应梯度、优化器状态与更新后参数 |
| 通过标准 | 各比较点的容差、允许差异及任务质量验收规则 |

对照运行时，优先加载已保存的随机输入与增强参数，而不是要求两个框架各自用相同种子生成“相同数据”。JAX 的随机机制还区分按子 key 逐次采样与一次向量采样；仅改变随机调用组织就可能改变实际随机值。[21]

建议采用以下定位顺序：

```text
权重映射与最终输入
    → 输入投影 / 视觉 stem
    → 每个块的 attention、归一化和 FFN
    → 输出头与逐样本损失
    → 对应输入及参数的梯度
    → 一次优化器更新
    → 短程训练与完整任务评估
```

记录最早超过既定容差的边界，再对该局部使用相同输入单独比较。不要只盯最后一层：末端误差不能说明源头在哪里；同样也不能预设所有局部误差一定同号、一定随深度放大。修复一处后重新运行整条回归，避免多个差异互相掩盖。

### 3.4 数值精度契约：不能只写“使用 BF16”

补充材料重点涉及 GELU、attention、RoPE、RMSNorm 与视觉 stem 的实现路径。[13] 将这些经验通用化时，建议形成以下逐模块检查表，而不是统一改成某个精度或算子实现：

| 位置 | 需要逐项核对的语义与精度 |
| --- | --- |
| GELU / 门控 FFN | 近似形式及参数、激活与门控相乘的顺序、输入输出 dtype、对应梯度 |
| Attention | Q/K/V 轴含义、head/group 映射、缩放位置、mask 含义与广播、点积累加和 softmax 精度、cast 时机 |
| RoPE | 旋转配对布局、位置编号及偏移、频率与三角函数精度、旋转计算和降精度边界 |
| RMSNorm / 自适应归一化 | epsilon、归约维度、scale 的参数化方式与存储精度、条件分支及输出转换 |
| 视觉 stem / 位置嵌入 | 卷积或线性投影的布局、计算精度，位置嵌入相加与进入编码器的 dtype 边界 |
| 参数更新链路 | 参数存储、实际梯度、梯度归约、主权重（如有）及优化器状态的精度 |

**明确核查过的边界**：`jax.nn.gelu` 的默认参数是 `approximate=True`，因此不能把“JAX 的 GELU 默认精确”写成框架常识；应检查参考模型是否显式选择精确形式。[14] `torch.set_float32_matmul_precision("high")` 控制 FP32 矩阵乘的内部计算策略，不等于所有操作都固定使用同一种低精度实现，也不控制卷积精度。[15]

AMP 会按算子选择执行精度；张量表面 dtype 不足以说明完整计算路径。[20] 实施时记录 autocast 上下文、显式转换、matmul 与 convolution 后端设置，并核对所用并行策略的参数和梯度 dtype。需要明确的 FP32 局部路径时，应同时检查自动转换和后端内部精度，不能仅加一个 `.float()` 就宣布完成对齐。

本指南建议保留“易检查的参考路径”和“经过验收的高性能路径”。先定位并修正差异，再逐项恢复混合精度、融合后端与编译，重复前向、梯度和更新检查。精确 GELU、显式 einsum 或全 FP32 都不是通用的最优配置；是否采用，取决于参考语义、容差、任务质量和实测成本。

### 3.5 架构语义与初始化：与数值误差分开排查

补充材料将视觉语言前缀与动作 token 的联合 attention，以及新增投影层初始化，列为独立于精度的检查层面。[13] 对类似多模态或多专家结构，建议先写清“哪些 token 可以看哪些 token”，再检查代码如何实现。

建议覆盖拼接顺序、每段长度、位置偏移、mask 的允许/屏蔽约定与广播维度、GQA 的 head 映射，以及拆分后送入哪个投影或专家。不能仅凭“拼接后算一次”或“分别处理再合并”判断正确性；等价与否由上述语义和对照结果决定。用不等长序列、padding、缺失模态以及受支持的不同 head 配置测试边界，避免硬编码只在一个变体中恰好成立。

若模型规定前缀不能读取动作 token，可在固定随机状态后改变动作输入，检查前缀输出是否保持在既定容差内。这是针对该可见性约定的测试，不是所有多模态模型的统一规则。

初始化审计则按“已从 checkpoint 完整恢复”与“实际新建或重置”分类。对后一类记录分布、fan-in/fan-out、缩放、截断和 bias；做单步对照时直接使用同一份初始张量。固定标准差的 normal 与随 fan-in 变化的初始化，不能仅因都叫正态分布就视为等价。

**微调阶段也不能自动跳过初始化检查。** 只有相关参数及状态在使用前被 checkpoint 完整覆盖，且初始化未改变后续使用的随机输入等状态时，这部分初始化才不再影响该次对照。新增头、适配器或重置模块均需要单独检查；这条条件化建议不同于补充材料对其特定 SFT/RL 场景的概括。

## 4. 正确测量整条训练流水线

### 4.1 覆盖训练循环与外围开销

至少标记以下逻辑区间；这只是分析划分，不表示它们一定串行执行：

```text
取数与解码 → 主机到设备传输及预处理 → 前向与损失
          → 反向与梯度通信 → 优化器更新

外围：启动/编译、日志、验证、模型保存、数据切换与恢复
```

PyTorch Profiler 可记录 CPU/设备活动、算子形状和内存信息，并通过 `record_function` 标记自定义阶段。[3] 建议分两种运行模式：

**定位模式**：只采集有代表性的短窗口，保留执行时间线，观察数据等待、拷贝、计算、通信和跨进程差异。

**验收模式**：关闭详细 profiler，保留轻量计时与必要日志，测量真实吞吐。详细采样得到的速度不要直接当作最终成绩。

### 4.2 计时必须处理异步执行

GPU 操作通常异步提交，普通 CPU 计时可能只测到提交工作，而不是工作完成。PyTorch 官方文档要求通过适当同步或设备事件获得准确时间。[4]

推荐按一个足够长的连续窗口测量：开始前完成预热并等待旧工作结束，窗口内保持正常流水，结束时等待相关设备工作完成。不要为了逐阶段计时，在每个算子或阶段后强制全局同步；这样会改变被测系统。

多卡测量在窗口开始前对齐进程，结束后汇总各进程耗时和完成样本数，以覆盖最慢进程的口径计算全局吞吐。汇总统计本身放到被测窗口之外。设备事件只能计量其依赖覆盖到的工作，不能用一条流上的事件代替完整多流、多卡墙钟时间。

### 4.3 看关键路径，不累加重叠区间

算子耗时、拷贝耗时、通信耗时可能相互重叠，其总和不一定等于 step time。也不要将多条通信流的耗时简单相加，作为训练等待时间。

分析通信时区分：

- **通信活动时间**：执行时间线上通信活动区间的并集。
- **与计算重叠的时间**：通信活动与约定计算活动区间的交集。
- **关键路径暴露时间**：由于通信尚未完成，确实推迟了后续必要计算或更新的时间。

前两者可以定义一个描述性的重叠率，但它不自动等于被隐藏的真实开销比例。每次比较应保持计算方法一致，并最终核对端到端耗时。

### 4.4 预热、重复与异常处理

可将“若干十步预热、数百步测量、至少三轮独立重复”作为初始测试方案，具体窗口应按编译耗时、数据变化和测量噪声调整。它们是建议起点，不是合格阈值。

预热应覆盖常见形状、工作进程启动及编译缓存建立。真实数据切换、评估或保存产生的尖峰应单列解释，不能为了让曲线平滑随意剔除。对收益接近噪声的改动，优先增加重复或采用交替 A/B 测量，不立即宣布有效。

## 5. 数据链路：先避免无效工作，再提高供给能力

### 5.1 从有效输入定义开始排查

对每类输入建立以下追踪表：

```text
数据来源 → 是否真实存在 → 是否参与模型/损失
        → 何时被屏蔽 → 屏蔽之前执行了哪些操作
```

候选问题包括无效相机占位、超长填充、无效时间步和重复的确定性变换。删除前必须确认其不承担缺失模态提示、位置编号、状态更新或其他训练语义。

**不能通过像素是否全零来判断一张图像是否无效。** 应使用数据模式、显式有效性标记或经过验证的掩码定义；真实黑色图像也可能是有效观测。

涉及输入裁剪时，建议设置以下验收要求：

| 风险 | 需要验证的事项 |
| --- | --- |
| 掩码语义变化 | 保留输入的可见关系、损失权重和归一化分母不变 |
| 位置语义变化 | 位置编码、模态编号、时间索引及输出对应关系正确 |
| 批内样本不一致 | 不能因部分样本缺失而删除其他样本的有效输入 |
| 分布式执行变化 | 条件跳过模块不能破坏所用并行实现要求的通信顺序 |
| 形状更加动态 | 编译重用率、重编译开销和批间负载仍可接受 |

可先处理数据集级固定无效字段，再测试按有效形状分组，最后评估逐批动态裁剪。动态形状与重编译的关系见第 7 节。[7]

### 5.2 调整数据供给，不盲目增加并发

官方调优指南支持通过 DataLoader 工作进程实现取数与训练的重叠，并强调工作进程数量应按工作负载及硬件调整。[5]

建议分别测量读取、解码、随机增强、组批和进程间传递，以确定真正等待发生在哪里。再逐步测试工作进程数、预取深度、工作进程复用和合适的存储组织，记录 CPU、主机内存及存储压力。

多卡任务应按整机预算检查“每个训练进程的工作进程数 × 训练进程数”，避免局部加并发造成整机争抢。缓存只用于不会改变语义的确定性结果；随机增强、依赖模型参数的结果，以及需要传播梯度的计算，不应被静默固化。

**验收**：真实数据上的取数等待缩短，端到端吞吐改善，数据分布和增强策略未改变，主机资源处于可持续范围。已驻留内存的合成数据只能帮助隔离瓶颈，不能替代真实数据成绩。

### 5.3 流式数据分片：同时覆盖数据并行 rank 与加载 worker

补充材料报告了一类不报错的故障：数据集虽然暴露 `getitem(idx)`，实际却按内部游标读取，导致外部 sampler 分配的索引没有决定实际样本；多 rank/worker 随后可能重复读取同一片数据。[13] PyTorch 文档也区分按索引访问的 map-style 数据集与由自身控制顺序的 iterable-style 数据集，并要求对后者的多 worker 副本显式防止重复。[16]

先检查数据接口是否兑现其契约。依赖索引的方案必须确认 `idx` 真正参与取数；流式或 chunk 模式则在实际读取层划分任务。不要在已经完成分片的数据上再叠加一套切分，否则可能漏读。

下面把补充材料的等差分片思路整理为独立示例，并补充 `num_workers=0` 的处理。这里 `rank/world_size` 指**数据并行采样空间**，不一定是整个作业的进程编号与进程总数；各 rank 必须使用同一 chunk 清单顺序和相同的 worker 数。

```python
def partition_chunk_indices(
    num_chunks: int,
    *,
    rank: int,
    world_size: int,
    worker_id: int = 0,
    num_workers: int = 0,
) -> range:
    """分配 chunk 清单的位置；无子 worker 时，主加载者按 worker 0 处理。"""
    values = (num_chunks, rank, world_size, worker_id, num_workers)
    if any(type(value) is not int for value in values):
        raise TypeError("all arguments must be integers")
    if num_chunks < 0 or num_workers < 0:
        raise ValueError("num_chunks and num_workers must be nonnegative")
    if world_size < 1 or not 0 <= rank < world_size:
        raise ValueError("require world_size >= 1 and 0 <= rank < world_size")

    workers_per_rank = max(1, num_workers)
    if not 0 <= worker_id < workers_per_rank:
        raise ValueError("worker_id is outside the effective worker range")

    global_worker_id = rank * workers_per_rank + worker_id
    stride = world_size * workers_per_rank
    return range(global_worker_id, num_chunks, stride)
```

其不重不漏的性质来自：所有加载者的起点恰好覆盖 `0 ... stride-1`，各自领取对应模类中的位置。该结论只针对**给定清单的位置划分**；不自动保证 chunk 内部无重复、过滤后样本完整、工作负载均衡或各 rank 的训练步数一致。

实际接入时，在训练主进程中取得并校验数据并行 rank/world_size，再作为普通可序列化元数据传给数据集；worker 内取得自己的 `worker_id` 和 worker 数。没有子 worker 时使用 `worker_id=0, num_workers=0`。不要依赖加载子进程继承训练通信组，也不要在预期多卡的任务中把获取 rank 失败静默退化为 0。[13][16][17]

如需每轮全局打乱，先依据共同的 epoch/种子生成同一份清单排列，再按位置分片。若各 rank 使用不同 worker 数、弹性扩缩容或动态任务队列，应另行定义分片与恢复协议；不能原样套用此公式。

### 5.4 验证实际样本覆盖，而不只验证分片函数

将以下检查放进小规模集成测试，而不是每步全量收集到训练热路径：

| 检查 | 建议的验收方式 |
| --- | --- |
| 样本身份 | 记录数据版本、episode/sample/frame 身份、epoch、rank、worker 与所属更新 |
| 非预期重复 | 比较不同 rank/worker 的实际输出，分离有意重复采样与实现错误 |
| 覆盖与遗漏 | 在有限测试集上检查输出集合及计数是否符合分片、过滤和尾批规则 |
| 多样性与负载 | 检查各 rank 的任务/场景分布、样本数与工作量，不能只比较 chunk 个数 |
| 跨轮与恢复 | 检查 epoch 打乱生效；恢复后既不重放已消费样本，也不跳过尚未消费样本，除非协议明确允许 |

至少测试 `num_workers=0`、多 worker、多个 rank，以及 chunk 数少于总加载者数的情况。最后一种情况可能产生空分片；同步训练需要显式处理步数不齐、空批与尾部结束，不能让某些 rank 提前退出而其余 rank 继续集合通信。

尾批策略必须纳入预期结果。以 `DistributedSampler` 为例，`drop_last=False` 会补充索引以便在副本间均分，因此不能要求任何配置都绝对无重复；跨 epoch 使用其 shuffle 时，还需调用 `set_epoch()`。[16] 对流式数据保存“训练已消费的进度”，并处理预取与 worker 游标领先于训练的情况；单独保存读取游标不足以说明恢复正确。

不要把“重复样本”直接描述为“每卡梯度必然完全相同”：随机增强、dropout 等仍可能不同。但非预期的数据重复本身就需要修复，不能因 GPU 都在忙而判定数据并行有效。

## 6. 传输与预处理：减少字节数，但保持数值语义

### 6.1 在合适边界选择紧凑表示

对于原始值确实为 8 位整数的图像，可测试保留 `uint8` 到设备，再按基线语义转换和归一化。相同元素数下，`uint8` 的图像载荷字节数是 `float32` 的四分之一；这只是表示大小的计算，并不意味着整个 batch、整个传输阶段或训练都会获得四倍加速。

不要把已经经过浮点插值、增强或归一化的数据直接压回 `uint8`，并宣称无损。深度值、点云、状态量和动作等，也不能套用 RGB 图像的表示假设。

迁移预处理位置时，用同一原始样本比较最终模型输入；核对插值、舍入、裁剪、通道次序、归一化顺序及随机增强参数，再比较实际传输字节数和完整耗时。

### 6.2 异步提交不等于设备端重叠

`non_blocking=True` 可以避免部分主机等待，但不自动证明拷贝与 GPU 计算并行。实现 H2D 与计算重叠还涉及 pinned memory、可并行的复制流和硬件条件。[6]

实施时应明确“何时可以复用源缓冲区”和“何时消费者可以读取目标数据”，并验证流之间的依赖。不能一边异步拷贝，一边提前修改其源数据。也不要在训练主线程中临时执行一次 `pin_memory()` 就假定会更快；应对完整数据路径做对照测试。[6]

**验收**：模型输入通过回归，时间线显示预期重叠或主机等待减少，端到端收益超过噪声，主机锁页内存开销可接受。

### 6.3 图像增强：随机参数粒度与统计粒度分别对齐

补充材料指出两种不同问题：整个 batch 共享一组增强随机参数，以及本应逐图计算的 contrast 统计跨 batch 聚合。前者改变随机性的组织方式，后者改变每张图的变换定义，不能混为一个“增强不一致”问题。[13]

建议分别记录并核对：

| 项目 | 要明确的规则 |
| --- | --- |
| 随机参数 | 按图像、样本、时间序列还是视角组抽样；哪些维度独立，哪些维度共享 |
| 统计维度 | 均值、对比度等按哪些通道/空间维度计算；是否错误包含 batch 维 |
| 变换定义 | 增强顺序、数值范围、裁剪、插值与归一化边界 |
| 随机状态 | 种子与子流如何分配给 rank、worker、epoch 和样本；是否可以回放 |

对独立图像批次 `(B, C, H, W)`，逐图标量参数可以表示为 `(B, 1, 1, 1)` 后广播；它与一个全批共享标量不是同一随机语义。**逐图独立不等于必须写 Python 循环**：先保留容易验证的参考实现，再测试保持相同抽样与统计规则的向量化或编译版本。性能改写前，固定并回放同一批增强参数以隔离实现差异。

对于视频、历史观测或多视角输入，先遵循基线对“同一序列/视角组是否共享几何或颜色变换”的约定，再决定独立粒度；不能把案例中的 per-image 策略扩展成所有时序与多视角任务的强制规则。这是本指南补充的适用边界。

建议加入一个隔离测试：固定某张图及其增强参数，只替换 batch 中其他图像；若设计为逐图独立变换，该图输出不应随其他图变化。另检查参数抽样粒度是否符合约定，而不是仅凭增强后的图“看起来不同”验收。JAX 使用 `vmap` 时也要核对输入 key 的拆分；向量化操作本身并不代替独立随机 key 的组织。[21]

## 7. 计算路径：编译、融合与形状管理

`torch.compile` 的收益与可编译区域、图中断和重编译行为有关；官方文档提供了图中断、动态形状和重编译的诊断方法。[7] 因此，不把“成功开启编译”作为优化完成的证据。

建议先选择重复调用、执行占比高、边界清楚的模块进行对照，而不是一开始就编译整个训练程序。每个候选区域记录以下结果：

| 问题 | 检查方式 |
| --- | --- |
| 编译是否覆盖目标热区？ | 对比编译前后的执行轨迹与调用结构 |
| 是否频繁退出编译区域？ | 检查图中断位置，区分必要边界和可消除问题 |
| 不同输入是否反复编译？ | 记录形状/控制流变化及重编译次数 |
| 稳态收益是否覆盖启动成本？ | 分开测量编译耗时和后续节省时间 |
| 数值与显存是否变化？ | 运行前向、梯度、更新回归并测量峰值显存 |

需要动态输入时，比较“少量稳定形状分组”和“动态形状编译”的整体效果；不要仅为减少重编译而丢弃有效内容。动态输入裁剪、批次组织与编译策略应联合测试。[7]

可用以下估算帮助判断短作业是否值得编译：

```text
预计净节省时间 ≈ 后续更新次数 × 每次更新节省时间 − 额外编译时间
```

这一估算假定后续性能相对稳定；频繁重编译时应把额外编译时间全部纳入。最终仍以实际完整作业时间验收。

混合精度、替换注意力后端和自定义融合算子属于需要单独回归的候选项。不要在同一实验中同时更改精度、损失和编译范围，使性能与质量变化难以归因。

## 8. 分布式通信：先有可调度的结构，再谈重叠

### 8.1 先确认问题是否来自通信

当时间线显示通信等待时，先检查它的上游原因：是否某个进程取数较慢、输入更长、计算分支更多，或提前进入了保存/日志逻辑。所有进程等待一个落后进程，不应一律解释为网络带宽不足。

将“通信量过大”“通信调用过碎”“调度过晚”“进程负载不均衡”作为不同假设，分别寻找证据，不用一个预取开关处理所有问题。

### 8.2 分片粒度与预取是联合设计

FSDP2 的 `fully_shard` 调用边界决定通信分组；按层自底向上组织分组可为通信与计算重叠提供机会。其通信与预取机制不同于旧式 FSDP，接口不能混用。[8][9]

建议按如下顺序测试：

```text
确认项目支持的并行实现及状态保存方式
    → 选择分片边界
    → 检查实际通信分组和执行顺序
    → 评估已有重叠与额外预取
    → 在显存预算内调整分组粒度和预取深度
```

分组候选可以是单个重复块或若干相邻块。不同模块不必采用同一粒度；应比较每组计算时间、通信调用数量、峰值显存和完整更新耗时。

**不要把“分得越细”或“预取得越深”作为固定目标。** 更细的分组需要验证调用成本；更积极的预取需要验证并发存活参数的显存代价。选取的是通过测量证明有效的配置，而不是开关最多的配置。[8][9]

### 8.3 尊重版本与框架封装边界

FSDP1 的包装器参数、FSDP2 的模块方法，以及训练框架对二者的封装，不是同一套配置系统。实施前记录实际版本、并行类型、模型支持范围和配置映射，检查是否存在配置被忽略或回退。

对 FSDP2，还要检查优化器初始化与分片后的参数是否匹配，并通过正常模块调用触发所需的前向钩子。[8] 通信重构后重新执行分布式与断点恢复回归，而不是只做一次前向冒烟测试。

**验收**：暴露在关键路径上的通信等待减少，总更新耗时改善，显存有余量，各进程执行稳定，质量与恢复测试通过。没有出现预期收益时，回看分组和调度证据，而不是继续叠加环境变量。

## 9. 显存：把节省出来的空间重新投入有效优化

### 9.1 区分活跃张量、缓存与其他占用

PyTorch 的 allocated 与 reserved 不是同一个指标；设备级占用还可能包含通信库等非 PyTorch 分配器管理的内存。[4][10] 因此，`reserved - allocated` 不能全部称为“碎片”，也不能只看设备监控工具的一个占用值判断问题。

建议在前向、反向、更新、验证和保存等不同阶段采集峰值。对疑似碎片问题，再使用内存快照判断分配模式，而不是直接将显存不足归因于碎片。

`expandable_segments` 面向分配尺寸变化等场景，是需要按平台和分配器条件验证的选项，不是普遍有效的显存修复开关。[4]

### 9.2 逐模块标定激活重计算

激活重计算通过在反向时重做部分前向计算，降低保存中间张量的需求。[11] 是否值得启用、在哪里启用，应由模块的显存收益和实际时间代价决定。

建立一个小型候选矩阵：

| 候选 | 模块 A 的重计算 | 模块 B 的重计算 | 要回答的问题 |
| --- | --- | --- | --- |
| C0 | 当前配置 | 当前配置 | 建立现状 |
| C1 | 减少 | 不变 | A 是否值得用显存换速度？ |
| C2 | 不变 | 减少 | B 是否值得用显存换速度？ |
| C3 | 使用验证过的组合 | 使用验证过的组合 | 联合配置是否仍有稳定收益？ |

记录实际重计算边界，不只记录一个含义不明的 `stride`。同名配置在不同项目中可能代表不同粒度。

重计算区域中的随机操作和前后向状态必须保持语义正确。PyTorch 文档明确说明随机状态保存及前后向执行不一致的风险；不要将关闭 RNG 状态保护作为无条件优化。[11]

### 9.3 资源预算变化后重新调参

当通信分组、输入形状或分配模式改变后，应重新测量，而不是沿用原来的重计算和微批设置。可将新增可用显存分配给三个候选方向：减少昂贵模块的重计算、提高适合的微批大小、增加有收益的预取。

这三种选择互相竞争，必须联合比较。不要把显存占满本身当作目标；应为最长输入、验证/保存、通信缓冲及长时间运行预留余量。

**验收**：在代表性极端输入和周期性操作下不发生 OOM，重复运行稳定；新增显存成本带来的端到端收益值得保留。

## 10. 优化器、日志与运行时：按真实占比投入

### 10.1 优化器融合

PyTorch 的优化器可能提供普通逐张量、`foreach` 和 `fused` 实现；支持条件与内存成本不同，通常需要对照测量。[12]

尝试替换实现时，保持参数组、学习率、权重衰减、epsilon、动量设置和裁剪顺序一致，比较一次更新后的参数及优化器状态。再检查长期训练、状态保存和恢复，不把“能运行”作为等价依据。

### 10.2 减少不必要的主机等待

训练循环中的设备张量打印、`.item()` 和设备到主机的数据读取等操作可能触发同步。[5] 优先排查每步读取大量标量、复制预测结果和依赖设备结果的 Python 分支。

可以按已约定的频率聚合和输出诊断信息，但应保留必要的异常检测。评估和保存也应单独计量；性能比较不能只在优化版本中降低这些操作的频率。

### 10.3 不为微小或不确定收益增加长期复杂度

垃圾回收、预取深度、分配器选项和其他运行时配置都应作为独立实验项。没有证据时，不默认关闭垃圾回收、不周期性强制清缓存，也不长期保留只能在单次运行中观察到的“加速”。

**验收**：收益可重复，正确性和可观测性不降低，代码维护成本与收益相称。优化器只占很小比例时，结束这一方向的搜索通常比继续微调更合理。

### 10.4 依赖与补丁：让语义差异可追溯

补充材料采用自包含组件替代覆盖第三方安装文件的 monkey-patch，以便直接追踪与参考实现的差异。[13] 可推广的是**明确依赖边界和可验证行为**，而不是“必须重写框架”或“使用第三方组件必然不正确”。

本指南建议优先使用显式配置、受控适配层或局部替换；确需维护分叉时，锁定版本、记录每项差异及其回归测试。避免安装过程中悄悄覆盖环境中的第三方源码；若暂时保留补丁，启动时检查目标版本和补丁是否实际生效。依赖升级后重新运行数值、数据和权重转换测试，而不只检查导入成功。

## 11. 迭代与归因：区分直接收益、使能价值和交互效应

### 11.1 每次改动都带着可检验假设

推荐使用以下实验句式：

> 由于基线时间线显示【证据】，预计【改动】将减少【关键路径上的具体等待/计算】，并可能改变【显存、通信或数据分布】；若【正确性或性能条件】不满足，则回滚。

每轮优先改变一个因素；有明确依赖的因素可以组成小型联合实验，但要标明依赖关系。对大改动保留开关、测试和独立提交。

将候选收益分为三类：

| 类别 | 主要价值 | 评价方式 |
| --- | --- | --- |
| 直接加速 | 当轮更新耗时下降 | 在相同基线上做重复 A/B 对照 |
| 降低资源占用 | 释放显存、主机内存或带宽 | 检查是否解决约束，以及有无额外时间代价 |
| 为后续优化创造条件 | 改变通信结构、形状或可用预算 | 与后续改动联合验证，并单列其使能作用 |

### 11.2 正确报告累计加速

对基线 B0、改动 A 和依赖于 A 的改动 B，最小对照可以是：

```text
B0
B0 + A
B0 + A + B
```

只有当 B 在原结构上独立有效且实现合法时，才补充 `B0 + B`。每项增量必须注明它是相对哪一个工作点测得的。

在有效工作量相同时：

```text
总加速比 = 基线耗时 ÷ 最终耗时 = 最终吞吐 ÷ 基线吞吐
```

不要直接相加不同基线上的百分比，也不要把各自独立实验的加速比相乘预测组合收益。连续实测阶段的相邻加速比可以代数连乘得到总比值，但这不证明各优化彼此独立。

### 11.3 给局部优化设置收益上界

若一个完全串行、未被重叠的阶段占总耗时比例为 p，且被加速到原来的 s 倍，可作如下理想估算：

```text
整体加速比 = 1 / ((1 - p) + p / s)
```

例如，某阶段只占总时间的 5%，即使其耗时降到零，理论上整体也仅约加速 1.053 倍。这是用于排序的简化推导；实际流水线存在重叠和资源竞争时，必须回到完整测量。

## 12. 扩展性：区分强扩展、弱扩展和质量目标

**强扩展**固定总工作量，增加资源后比较完成时间；**弱扩展**固定每个资源单元的工作量，增加资源时总工作量也随之增加。两种测试回答不同问题，报告中应明确标注。

相对使用 N₀ 个资源单元的基线，使用 N 个资源单元时，可定义：

```text
吞吐扩展效率 = Q(N) / ((N / N₀) × Q(N₀))
```

Q 是统一口径的全局吞吐。固定总工作量时，也可用耗时比计算对应效率。输入形状、计量单位和配置变化需要同时披露。

扩容报告建议回答三个独立问题：

| 问题 | 应保持或披露的条件 |
| --- | --- |
| 系统能否高效扩展？ | 相同软件与模型实现、输入规则，以及明确的强/弱扩展口径 |
| 模型能否按目标质量训练？ | 全局批大小、更新次数、学习率等变化及对应质量验证 |
| 扩容是否值得？ | 实际完成时间、总 GPU 小时、失败重试与存储/网络限制 |

弱扩展下维持每卡微批，通常会改变全局批大小；更高 samples/s 并不自动代表达到同等质量更快。单机和多机使用不同代码或进一步优化后的基线时，也应单列版本，不能将其混为同一个对照。

## 13. 权重转换与部署：加载成功只是第一道门槛

### 13.1 为每条转换路径定义张量映射

补充材料将 JAX、旧 PyTorch、新实现、SFT 产物与部署格式之间的转换单独处理，具体涉及 Q/K/V 合并、MLP 权重转置/堆叠，以及包装器前缀清理。[13] 通用经验是：**转换是模型语义的一部分，不只是 key 重命名。**

建议为每条路径维护转换清单：源/目标模型配置、格式版本、键名、形状、轴含义、dtype、重排规则和允许丢弃/补全的项目。重点检查：

| 风险点 | 必须显式规定的内容 |
| --- | --- |
| Linear / 卷积布局 | 输入输出轴和卷积维度；何时 transpose/permute |
| Q/K/V | 拼接顺序、拼接轴、是否存在独立 bias、head/group 维如何还原 |
| 门控 FFN | gate/up 顺序，stack/concat 的轴，down projection 的方向 |
| 包装器与分片 | 只按白名单清理实际存在的前缀，并检测重名；分片/展平参数按对应保存协议恢复 |
| 参数与缓冲区 | 除权重外，核对必要 buffer、共享/绑定关系与加载后的实际 dtype |

方阵转置、同形状的 Q/K/V 顺序错误等，可能保持键名与形状不变；因此形状检查不能证明数值语义正确。FSDP 等分片状态也不能仅通过删除名字前缀变成完整权重。

### 13.2 严格加载、数值回归与产物溯源缺一不可

PyTorch 的 `load_state_dict(..., strict=True)` 要求状态字典的键与模型匹配；这是必要的加载检查，不是权重语义等价的证明。[19] 本指南建议采用以下验收链：

```text
检查源权重和模型配置
    → 执行有版本的映射规则
    → 检查键名、形状、dtype、必要状态与共享关系
    → strict=True 加载最终目标模型
    → 固定输入下比较关键中间值与最终输出
    → 继续训练用途增加梯度/更新与恢复检查
    → 在实际部署运行时复核完整预处理、模型与输出后处理
```

能精确逆转的纯重排转换可增加往返测试；存在精度降低、删除字段或单向格式变化时，必须声明不可逆部分，不能要求或宣称无损往返。不要通过随意 `strict=False`、忽略键或零填充缺失参数来让转换“成功”。有意丢弃的项目应预先列入转换规则，再对最终目标严格加载。

若旧格式要求补回兼容性字段，只能使用来源明确、配置匹配且用途经过检查的参考状态，并记录到转换清单；不得从任意同名模型拼凑训练参数。无法确认时应终止转换。补充材料中的 reference-model 方案是其特定格式的兼容措施，不是一般性的缺权重修复方法。[13]

输出产物至少附带源 checkpoint 标识或哈希、源/目标配置、转换器提交、目标 dtype 和验证记录。针对 VLA 等策略，部署验收还应纳入相机顺序、tokenizer、状态/动作归一化及动作后处理；不能只在转换脚本内运行一次模型前向。

### 13.3 区分训练恢复产物与部署产物

建议明确每个导出文件属于哪种用途。只导出模型权重可用于推理或重新启动训练，但不自动构成原训练状态的精确恢复。要声称断点续训一致，还需要核对优化器、调度器、随机状态及数据消费进度，参照第 3.1 与第 5.4 节。

新格式到旧格式、训练态到部署态都应独立验收；不能用一条转换路径通过，替代全部方向的验证。导出所需的配置、归一化统计和兼容性信息应与权重一起交付。

## 14. 可直接执行的工作流程

| 阶段 | 主要工作 | 进入下一阶段的条件 |
| --- | --- | --- |
| A：建立基线 | 锁定环境、模型和数据，定义指标；迁移任务先完成参考契约、分片和转换审计 | 基线可重复，输入、实现、训练与恢复正确 |
| B：定位问题 | 短窗口执行剖析、资源采样、真实数据吞吐测试 | 存在有证据支持的主瓶颈假设 |
| C：选择实验 | 评估收益上限、依赖、语义风险与改动成本 | 实验可回滚，验收条件事先明确 |
| D：实施与回归 | 最小改动，分层正确性检查，重复性能测试 | 正确性通过，收益或使能价值有证据 |
| E：更新配置 | 重新分配显存/通信/批次预算，刷新性能画像 | 新工作点稳定，下一瓶颈明确 |
| F：最终验收 | 长程训练、任务评估、边界输入、保存恢复、部署导出与必要的扩容测试 | 达到项目预先约定的质量和性能目标，产物通过用途对应的验收 |
| G：沉淀交付 | 保存配置、提交、原始测量、测试及结论 | 另一位执行者能够复现并回滚 |

**停止条件**：目标已经达到；剩余候选收益落入测量噪声；预计收益不足以覆盖实现维护成本；或在当前硬件/软件约束下无法进一步验证。此时记录限制和后续触发条件，不把未经测试的方案写成已完成成果。

## 16. 常见误区速查

| 误区 | 应采用的判断 |
| --- | --- |
| GPU 利用率高，就没有优化空间 | 检查有效工作量、关键路径和完成任务的时间 |
| 被掩码屏蔽的内容可以直接删除 | 先验证其完整语义、位置关系和分布式执行要求 |
| 图像传输字节数缩小四倍，训练就会快四倍 | 只在同元素数的表示比较中成立；整体收益必须实测 |
| 开启异步传输或预取，就已经实现重叠 | 用执行时间线和完整耗时验证 |
| 每个模块应使用同一种重计算策略 | 按模块成本及联合显存预算选择 |
| reserved 与 allocated 的差值全部是碎片 | 结合缓存机制、内存快照及设备级占用分析 |
| 开关越多，系统越快 | 保留经过验证的最小有效组合 |
| 改小真实输入或减少任务信息也是等价加速 | 将其作为任务/训练方案调整，重新评估质量 |
| 一条 loss 曲线相近就足以宣布精度不变 | 使用分层数值回归和对应任务质量评估 |
| 多卡吞吐扩展好，就一定缩短收敛时间 | 区分扩展性、训练协议变化与达到目标质量的时间 |
| 模型名称和 BF16 配置相同，两个实现就等价 | 逐模块核对数值路径、结构语义、数据及权重映射 |
| 配了 DistributedSampler，实际样本必然不重不漏 | 检查数据接口是否使用索引，并验证真实 rank/worker 输出 |
| per-image 增强必须串行执行，或所有观测都应独立增强 | 区分随机共享与统计粒度，验证等价向量化，并遵守时序/多视角协议 |
| strict=True 加载成功，就说明转换正确 | 继续检查轴语义、张量数值、输出及用途对应的恢复/部署行为 |
| SFT/RL 阶段无需关注初始化 | 检查实际新建、重置、未恢复的参数及随机状态影响 |

### 不直接泛化的说法与核查结果

| 补充材料中的概括 | 本指南采用的边界及依据 |
| --- | --- |
| “JAX 的 nn.gelu 是精确形式” | 框架 API 默认 `approximate=True`；参考模型是否显式选精确形式，应查对应提交。[14] |
| `"high"` 等于所有 FP32 matmul 都按同一 TF32 路径执行 | 它是内部精度策略，受可用算法影响，且不控制卷积；不能由开关名推断全部算子的实际路径。[15] |
| “JAX 的设备都在单进程内，天然不存在这类分片问题” | JAX 同样支持多进程/多主机。应按真实数据装载与设备布局验证，而非用框架名称或 SPMD/MPMD 标签替代检查。[18] |
| “spawn worker 内 dist.get_rank() 永远返回 0” | PyTorch 未初始化默认进程组时的直接调用会报错；静默得到 0 可能来自应用层回退逻辑，不是该 API 的普遍行为。[17] |
| 固定标准差 normal 与参考初始化“对齐”，且初始化不影响 SFT/RL | 来源同时描述了不同初始化方式，不能据此证明分布一致；影响取决于相关参数和状态是否被完整覆盖，见第 3.5 节。[13] |
| `strict=True` 可排除全部权重转换错误 | 严格键匹配不能排除同形状的轴重排、权重顺序及配置错误，需继续做数值与端到端验收。[19] |

来源中为特定实现采用的逐图循环、自包含重写及特定转换模式，不提升为所有项目的强制方案。本指南新增的分片边界处理、时序增强限制与部署清单属于工程推导和建议，而不是来源声称已完成的额外实验。
